# ADR 0011 - Real traffic, and proving the recommendations are worth anything

**Status:** accepted

## Context
Every number the project could quote was about throughput: events per second,
batch duration, recovery time. Nothing said whether the recommendations were
any *good*. They could not, because the traffic was generated by a rule
(`catalog.AFFINITY`) that the pipeline then rediscovered — a closed loop that
can only confirm itself.

Generated traffic is still the right default: it starts with one command, needs
no download and no account, and makes the pipeline's behaviour checkable at a
glance. But a portfolio project claiming a recommender has to answer "compared
to what, on whose data".

## Decisions

- **RetailRocket for real traffic.** 2.7M events from a real shop over four
  and a half months (views, add-to-carts, transactions), with visitor ids and
  item ids. It is the smallest public dataset that has the two things this
  pipeline needs: repeat visitors, and events rather than only completed
  orders. `scripts/fetch_dataset.py` downloads it and verifies the row counts
  and column names, so a changed export fails immediately rather than halfway
  through an evaluation.

- **Visits are cut at 30 minutes of inactivity.** The dataset has no session
  id, only a visitor id. Keying co-occurrence on the visitor alone would pair
  products a shopper saw three weeks apart — the pipeline would be measuring
  "the same person eventually looked at both", not "these go together". Thirty
  minutes is the long-standing web-analytics convention, and it is one
  constant (`SESSION_GAP_MINUTES`) if a different value is wanted.

- **Replayed on the replay's own clock.** The events are from 2015. Sent with
  their original timestamps, every window the pipeline wrote would sit eleven
  years in the past: the API's lookback would return nothing, the dashboard
  would look broken, and the state store would carry watermark state for a
  period nothing else references. So timestamps are mapped onto the replay's
  own clock — same order, same relative spacing, divided by a fixed speedup.
  A week in five minutes is ~2000x; the replay reports the factor and warns if
  the longest visit, once compressed, is wider than the co-view gap (which
  would silently stop its products pairing).

- **Deterministic event ids.** `session-sequence`, derived from the data
  rather than a UUID, so replaying the same slice twice hits the same upserts
  instead of double-counting. This is what makes a replay safe to repeat.

- **The replay closes its own windows.** Structured Streaming advances a
  watermark on event time, and during a replay the replay is the only source
  of it. When it stops, the windows holding its last minutes never close - on
  a five-minute slice that is most of the last two minutes of data, silently
  missing from every pair count. The replay therefore ends by sending a
  handful of events whose timestamps run past the end of the slice. They use
  one reserved product id (-1) and a fresh session each, so they can form no
  pair, and their own trending rows are deleted once Spark has written them.

- **Real items get real labels, not invented ones.** RetailRocket hashes its
  item properties: there are no product names or prices, only category ids.
  The catalogue built for a replay says `Item 214536500`, `cat-1037`. Inventing
  plausible names would make the screenshots prettier and the project dishonest.

- **Hit-rate@10 on held-out days, against bestsellers.** Train on the days that
  were replayed; test on the days after, which the pipeline never saw. For each
  test visit, hand the model the first product and ask for ten; score a hit
  when the product the shopper viewed *next* is among them. The baseline
  answers with the ten most-viewed products of the training period — what a
  shop does with no recommender at all, and a harder baseline than it sounds,
  because popular products are popular for everybody.

- **The model's answers come from the running system.** `--source api` asks
  the live `/related-products` endpoint, fallback and all, so the number
  measures what a client would actually receive. `--source mongo` reads the
  pair table directly, which isolates the co-occurrence signal from the
  trending fallback. Both are reported with coverage — the share of queries
  that got a real answer — because a model that answers 5% of queries
  perfectly is not a good model, and an average that hides that is not an
  honest number.

## Rejected

- **Inventing session ids per visitor-day.** Cheaper than an inactivity gap
  and wrong in both directions: it splits an evening visit at midnight and
  merges a morning and an evening visit into one.

- **Precision/recall over the whole basket.** Tempting because the numbers
  look bigger, but "did anything recommended appear later in the visit"
  rewards recommending popular products. Next-item is the stricter question,
  and the one a "customers also viewed" strip is really answering. The
  looser number is still reported next to it, labelled as such.

- **Training an ML model now.** The point of this phase is a measured
  baseline for the streaming co-occurrence the pipeline already computes. A
  ranker has something to beat only once that number exists.

- **Committing the dataset.** 1.4 GB, and redistribution is not ours to do.
  `data/` is git-ignored, the fetch is one command, and the manifest records
  exactly which files the numbers came from.

## Consequences
The README can state a measured quality number next to the throughput ones,
and say what it was measured against. The evaluation is reproducible by anyone
with a Kaggle account: fetch, replay, evaluate — three commands. And because
the harness scores any callable, an ML ranker added later is a few lines, not
a rewrite.
